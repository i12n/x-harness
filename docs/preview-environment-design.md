# 测试环境 / 人验收环境设计

> 目标：让"验收"这件事有人能**点开看、点一下、当场判断**，而不是只读卡片上的文字。
> 本文只做设计；实现拆成 TASK-1226（证据式）与 TASK-1227（预览主机）。

## 1. 人要验收什么（先把验收动作拆开）

| 类型 | 人的动作 | 能不能靠文字/证据 |
| --- | --- | --- |
| 视觉/布局（如"间距够不够大"） | 看一眼截图 | **可以**——截图就够 |
| 交互/流程（如"点播放全部会不会报错"） | 真点一遍 | 需要能跑的环境 |
| 数据/边界（如"没有数据时的空状态"） | 造数据看 | 需要能跑的环境 + 可写的库 |
| 回归（桌面端没被改坏） | 对比例图 | 截图 + 已验证的命令 |

结论：**一半的验收截图就够，另一半必须有能跑的环境。** 所以设计分两阶段。

## 2. 现场事实（2026-10-02 实测，决定了方案取舍）

| 事实 | 影响 |
| --- | --- |
| 生产机 `/` 已用 **89%（剩 3.7G）** | **不能**把预览栈放生产机：x-music 镜像 1.2G + 依赖 + 库，随时撑爆 |
| 生产机 2 vCPU / 1.9G（已用 782M） | 再起一个 Node 应用 + DB，会挤到 x-music 生产 |
| 生产机 Caddy 只服务 `rehelu.net → app:3000`，3000 仅本机 | 加预览路由 = 改生产 Caddy，与部署文档"不改 Caddy、不新增对外端口"冲突 |
| 阿里云 `47.100.5.48`：2 vCPU / 1.6G / **33G 空闲**，未装 harness | 适合当预览主机（资源够、互不影响） |
| 执行档案里的 `commands.install/test/build` 至今**没有任何消费者** | 预览构建正好用上它，不用新造字段 |
| x-music 已有 `test:e2e`（Playwright） | 截图不需要从零搭 |

## 3. 三条路线

| 路线 | 做法 | 结论 |
| --- | --- | --- |
| A｜**证据式预览** | 在 Run 的容器里跑 `install/build`，产出构建结果 + **截图** + 产物归档，随验收卡推给人 | ✅ 本期做：零基础设施改动、零生产风险 |
| B｜**独立预览主机** | 把构建产物送到阿里云机器，起一个带端口的容器，用那台机器的 Caddy 提供 `preview-<id>.…` | ✅ 作为 TASK-1227：交互/数据类验收需要 |
| C｜生产机同机预览 | 在生产机开端口/改 Caddy | ❌ 明确不做：磁盘、内存、生产隔离三条都不过 |

## 4. 拍板

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | 先做 A（截图 + 构建证据），再做 B（live 预览） | A 立刻可用且零风险；B 需要一台机器和域名决策 |
| D2 | 预览**构建**复用执行档案的 `commands.install/build`，在受限网络里跑（只放行包源） | 让死字段复活；预览不该有生产网络的自由度 |
| D3 | 截图按**验收标准里的视口/场景**生成，由工作项的 `checks` 或验收标准文本里的宽度（320/375/414）驱动 | 验收要的东西截图，不是"随手来一张" |
| D4 | 预览**永远不碰生产库**；需要数据时用一次性数据库，随预览销毁 | 已写进部署文档的原则 |
| D5 | 预览是**一次性资源**：有 TTL（默认 4h）、有并发上限（默认 1）、有显式 `预览停止` | 单机资源有限，防止忘记清理 |
| D6 | 验收卡同时给三样：**截图**、**证据包**、**预览链接**（B 阶段才有） | 人只需要一个地方点 |

## 5. A 阶段设计（证据式预览，本期）

```text
Delivery 进入 READY_FOR_RELEASE（或人执行 `预览 <deliveryId>`）
        │
        ▼
PreviewService.build(delivery)
   1. 取交付主任务的成功 Run → 其 worktree（保留中）
   2. 起一个 preview 容器：同一执行镜像，网络 restricted（放行包源），工作区只挂该 worktree
   3. 依次执行 profile.commands.install / build（缺失则跳过并显式说明）
   4. 若仓库有 e2e/截图脚本 → 按验收视口截图（320/375/414 …）
   5. 收集：命令结果、日志尾部、截图、产物 tar 的路径与大小
        │
        ▼
写 run.result.preview + 事件 PreviewBuilt；交付卡附截图与结论
```

失败模式：

- 没有 install/build 命令 → **不报错**，证据里写明"未配置构建，只有仓库验证命令的结论"；
- 构建失败 → 预览标记 FAILED，交付卡说清"应用起不来"，**不阻塞**验收（人可以选择只接受代码改动）；
- 截图脚本缺失 → 只给构建证据。

## 6. B 阶段设计（独立预览主机，TASK-1227）

```text
harness（生产机）                       预览主机（阿里云，独立 Caddy）
  build 预览镜像/产物  ── docker save | ssh 传输 ──▶  load + run -p <port>:3000
                                                    Caddy: preview-<id>.<domain> → 127.0.0.1:<port>
  验收卡给链接 + 一次性 token  ◀── URL ─────────────┘
        （TTL 到点由 harness 发 `预览停止` → 对端 stop + rm）
```

- 传输：优先 `docker save | ssh docker load`（无 registry 依赖）；产物大时再考虑私有 registry。
- 隔离：预览主机**只跑预览**，不跑 harness、不碰生产域名；每台机器的 Caddy 归 harness 所有。
- 鉴权：URL 带一次性 token（`?t=<random>`，Caddy 校验）或 HTTP Basic；预览消失即失效。
- 数据：需要 DB 时在预览主机起一次性 Postgres，迁移 + 种子后使用，随预览销毁。
- 资源：每个预览 `--memory 512m --cpus 0.5`；并发上限 1；TTL 4h。

## 8. 验收（可执行）

A 阶段：

1. 给一个 `commands.build` 成功的仓库 → 事件 `PreviewBuilt`，run 结果含构建结论与截图路径；
2. 构建失败 → `PreviewFailed`，交付卡说明"应用起不来"，验收仍可继续；
3. 未配置构建 → 不报错，证据里显式写明；
4. 截图按验收里的视口生成（320/375/414 至少三张，可断言文件名）。

B 阶段：

5. 预览链接在生产机之外可访问，带 token；无 token 403；
6. TTL 到点后容器消失、端口释放、链接失效；
7. 预览主机上不存在任何生产域名/生产库。

## 9. 任务拆分

```text
TASK-1226  证据式预览：preview.build/show/stop + 构建证据 + 验收视口截图 + 交付卡展示
TASK-1227  预览主机：产物传输、预览侧 Caddy、一次性 token、TTL/清理、一次性数据库
```

## 10. 风险

| 风险 | 应对 |
| --- | --- |
| 预览构建把生产机的磁盘/CPU 吃满 | 构建用容器 + 资源上限；磁盘 <5G 时拒绝构建（可用 `df` 前置检查） |
| 预览链接被外部访问 | 一次性 token + TTL；不做公开索引 |
| 截图与实际不一致（旧构建） | 截图与构建在同一次 PreviewService 调用里产出，带 runId 关联 |
| 人只看截图就放行交互问题 | 交付卡区分"已截图验证 / 需要真机交互"，B 阶段补上可点环境 |

# TASK-1267 验收意见 = 一次交付修订，而不是"退回某个任务"

> 状态：**已实现**（§2–§6）。§6 的第 3 步（删掉任务级打回路径）只做了一半：
> 验收阶段不再选任务，但"开发中还有卡住的开发点"这条老路径仍保留，见 §7。

## 1. 问题

真实验收场景：需求「x-music 添加下载歌曲功能」分为两个开发点，用户看完测试环境
在话题里发：

```text
做如下调整：
歌曲详情页的下载按钮，夹在播放和喜欢两个按钮之间，样式与其他两个按钮不统一。
需要对这三个按钮做统一的设计，风格统一且美观。
```

harness 的回应是反问：

```text
「x-music 添加下载歌曲功能：」：这项需求有 2 个开发点，重做哪些？
[在歌曲列表添加单曲下载按钮并实现统一单曲（已完成）]
[在歌曲详情页添加下载按钮并确认播放器无下（已完成）] [全部]
```

随后三轮追问暴露的不是三个小毛病，而是同一个根因：

1. 用户已经指名了目标，机器人还在问；
2. 反问没有可回答的通道（`scope`/`item` 被丢弃、没有 pending 状态）；
3. 就算能答，"退哪一条"也不该由用户回答——那是内部实现；
4. 而且"退回"的代价是重跑：整批退回会让**已经验收通过的部分被重新实现一遍**。

## 2. 根因

**用"退回某个 Task"来表达"改一处"。**

```text
验收意见 → 选择受影响的 Task → 把 Task 退回 READY → 调度器为每条各起一个 Run
```

这条链路把三件事绑死了：

| 绑定 | 后果 |
| :-- | :-- |
| 意见 → Task | 必须回答"退哪一条"，不回答就动不了 |
| 退回 → 重跑 | 每条被退回的 Task 都从 `origin/main` 重建工作区重新实现 |
| 全部退回 → 全部重跑 | 已验收通过的部分被重写，整个交付重新验收 |

所以"要不要问"和"重跑多少"其实是同一个设计缺陷的两个侧面：**意见的作用域被
错误地表达成了任务集合**。

## 3. 目标模型：修订（Revision）

把验收意见当作**对当前交付物的一次修订**，而不是对某些任务的退回。

| 维度 | 现状（打回） | 目标（修订） |
| :-- | :-- | :-- |
| 用户表达 | 意见 + （被迫）范围 | **只有意见** |
| 作用对象 | 若干 Task | 当前交付物 |
| 基线 | `origin/main` | **上一轮产物**（交付现状） |
| 旧 Task | 退回、重跑 | **保持 DONE，产物冻结** |
| 已验收部分 | 可能被重写 | 不动 |
| 产出 | 各 Task 各自的新 diff | 一条增量 diff，叠加在现状之上 |
| 交付状态 | 回 `IN_PROGRESS` | 回 `IN_PROGRESS`（多了一条未完成项） |
| 用户看到 | 开发点编号、范围问题 | "收到，这就改；改完我自动重跑并更新测试环境" |

一句话：**用户说"再改一处"，harness 就在现有交付上加一轮增量修订**——这正是
「在现有基础上做改进」。

## 4. 机制映射：尽量不造新概念

修订不是一个新实体，而是用现有构件拼出来的：

| 修订的要素 | 用现有构件实现 | 现状 |
| :-- | :-- | :-- |
| 一个可执行的工作单元 | 同一 Specification 下新增一条 Task + PlanItem | `createTask` / `createPlanItem` 已有 |
| 基线与仓库 | `TaskTarget.baseRef` = 上一轮产物的分支 | 字段与 `WorkspaceManager` 都已支持（`worktree add … <baseRef>`） |
| 排队执行 | 现有 Scheduler（`READY` → 新 Run） | 已有 |
| 交付回 `IN_PROGRESS` | 交付聚合看到有未完成 Task | 已有（reconciler） |
| 证据 / 评审 | 现有 diff / verification / reviewer | 已有 |
| 同一个 PR | 现有 `deployTest`（推测试分支 → 更新 PR） | 已有，但**有一处要修**，见 §5 |

用户侧不变：`验收意见 → 一条修订`。永远不出现任务、开发点、范围。

## 5. 需要补的三处

| # | 改动 | 落地位置 |
| :-- | :-- | :-- |
| 1 | 交付的"当前内容" = **最新**一次成功 Run 的工作区（原来取"第一个任务"，有修订链时会推旧产物） | `src/delivery/application/product.ts`；`DeployService.resolve()` 与修订入口共用 |
| 2 | "意见 → 修订任务"入口：同一 Specification 下新增 Task + PlanItem，`baseRef` = 交付现状，状态直接 `READY` | `src/command/handlers/revision.ts`（`delivery.revise`）；`actions.ts` 在验收阶段把意见路由到这里 |
| 3 | 回归不变式：新 diff 不得回退上一轮已通过的实现 | `src/domain/revision.ts` 的 `describeRevisionRegression`，在 `worker.ts` 里抬成 high risk 并进评审理由 |

验收标准：修订任务的验收项 = **上一轮已通过的验收项（回归）** + **意见本身**
（自然语言，作为人工确认点，与现有"人确认一次"的交付验收一致）。

## 6. 迁移

1. **修订落地** ✅：§5 的 1 + 2。验收阶段的一条意见 = 一条修订，旧任务保持 DONE，
   交付自己回 `IN_PROGRESS`，调度器自动起新一轮，同一个 PR 更新。
2. **证据变强** ✅（基础版）：§5 的 3。删掉上一轮改过的文件会被抬成 high risk
   并写进评审理由。
3. **收尾** ⏳：任务级打回路径还留着（见 §7），只服务于"开发中还有卡住/待评审的
   开发点"这种没有交付可修订的情况；`pickTargets` 因此还在。

## 7. 仍然保留的任务级打回路径

修订只在**所有开发点都已经完成**（没有人在等验收意见、没有还在跑的）时启用。
剩下的情况——需求还在开发中，但有卡住或等人评审的开发点——仍走老的打回路径：

| 规则 | 行为 |
| :-- | :-- |
| 不问 | 任何路径都不出现「改哪一个 / 重做哪一个」 |
| 读原话定范围 | 意见与标题共享 ≥4 字的最长片段 → 退命中里得分最高那一档（命中两条就两条） |
| 没点名 | 退用户刚在看的那条（`currentTask`），**不整批** |
| 一条消息多条命令 | 命令幂等键加序号，否则第二条被当 replay 静默丢弃（已修） |

§6 第 3 步就是把这条路径也收掉。

## 8. 打回一整批的代价（为什么避免它）

被打回的每条 Task 由调度器各起一个新 Run，基线是 `origin/main`（上一轮改动不在
基线里），交付回 `IN_PROGRESS`、整份交付重新验收——已验收通过的部分会被重新
实现一遍。所以即使在老路径上也是"宁可少退"：少退一条用户一句话可补，多退一条
要重跑整轮。修订模型把这件事从根上去掉了：**没有任何 Task 被退回**。

## 9. 风险

| 风险 | 处理 |
| :-- | :-- |
| `baseRef` 指向的分支被清理 | 工作区会清理，`ai/<task>-<run>` 分支必须保留；不可靠时改存 commit sha |
| 修订与旧任务的验收证据交叉 | 修订任务的验收项必须包含上一轮的回归项 |
| 多仓库 / 多 target | 修订的 `baseRef` 要按 target 逐个记录 |
| 意见过大（其实是新需求） | 意图层判成 `create` 时不走修订，照旧开新需求 |

## 10. 验收（可执行）

1. 用户发 §1 那段意见 → 同一条需求下出现一条修订任务（`baseRef` = 交付现状），
   旧任务保持 DONE，全程不出现任务编号与范围问题。
2. 修订跑完后推测试分支 → 测试环境上看到的是"上一轮产物 + 这次修订"。
3. 新 diff 删掉上一轮改过的文件 → 评审理由里出现"上一轮的改动被回退"。
4. `RELEASED` 冻结（引导开新需求）、机器侧失败重试的边界不变。
5. `npm run typecheck`、`npm test` 全绿。

无产物降级、交付现状取最新一轮、回归不变式）、`tests/requirementActions.test.ts`

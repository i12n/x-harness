# 阶段推进交互设计：每完成一步，问"下一步做什么"

> 状态：**P1 已实现**（卡片含具体下一步 + 一键按钮 + `prob-…` 句柄 + 三个节点主动发卡）；P2/P3 见 §7。
> 关联：`requirement-interaction-redesign.md`（需求=话题、不限定动词）、`conversation-binding-design.md`（会话绑定）、TASK-1216（卡片/按钮）、TASK-1244（user-level 动作）、TASK-1254（通过=阶段决定含义）。

## 0. 问题

现状是**单向播报**：Run 成功推一条「run-xxx SUCCEEDED」，测试部署成功推一条「✅ 测试环境就绪」，然后就没有下文了。

```text
机器人：✅ 测试环境就绪：dlv-9128847051   🧪 http://47.100.5.48:18080/
用户：（那我现在该干嘛？）
```

三个后果：

1. 用户不知道该说「通过」还是「发布」——动作全靠自然语言，等于要背动词表；
2. 用户在错误的话题里发指令（09:26 那次 `deploy.test` 报错就是这么来的）；
3. 卡住（BLOCKED）时只报"失败"，不给"重跑"的入口。

## 1. 设计原则

1. **一步一问，且说清下一步做什么**：问句后面必须跟"点下去会发生什么"——具体到动作、产物与地址。禁止只写"要不要继续下一步"。
2. **prob-… 是唯一追踪句柄**：进度查询与所有操作都能用最初的问题 id（如 `prob-950662cc5b`）发起和追溯；卡片固定带这个 id。
3. **主按钮唯一**：推荐动作 1 个（primary），次按钮 ≤ 2，危险动作（打回/放弃）用 danger + 二次确认。
4. **按钮 = 捷径，不是唯一入口**：自然语言意图解析保持不变，两者走同一套动作映射与阶段门禁。
5. **不猜**：按钮点下去先过门禁（`commandsForRequirementAction`），不满足就回一句解释，不静默失败。
6. **不打扰**：同一需求同一阶段只问一次；用户主动问进展时再给一次；通知合并进同一张"当前卡片"。
7. **可纠正**：卡片带 `requirementId + stage`，过期点击回复"这步已经做过了，现在在 X"并给当前主按钮；消息点名了 prob id 时，一律以点名为准。

## 2. 阶段 × 下一步（核心表）

"下一步"一列就是卡片上要写给用户看的内容：**会发生什么 + 产物/地址**。按钮标签用具体动作词，不用"继续"。

| 阶段 | 进入条件 | 卡片标题 | 证据行 | **下一步（写清楚）** | 主按钮 | 次按钮 |
| --- | --- | --- | --- | --- | --- | --- |
| 澄清中 | problem 未 CONFIRMED / 有 OPEN 澄清 | 「需要你确认」 | 待澄清问题 | 选定范围后我会推导规格并拆解任务 | 提交选择 | 放弃 |
| **规格就绪** | spec 推导完成、待开工 | 「规格已就绪」 | N 个工作项 + 验收标准 + 目标仓库 | 开工：按规格拆出 N 个任务并立即开始第 1 轮开发（约 10–30 分钟） | **开始开发** | 改需求 |
| 开发中（Run 结束） | Run 终态但阶段未变 | 「本轮结果」 | 验证项通过数 / diff 摘要 / 失败原因 | 失败：重跑会从 `origin/main` 新建工作区再跑一轮；成功：等它进入待验收 | Run 失败→**重跑**；成功→看看进展 | 打回 |
| **待验收** | 任务 DONE 或 REVIEW | 「做完了」 | 改动摘要 + 验证结论 | 推测试环境：把这次改动推到 `test/dlv-…`、开/更新 PR 并部署到 `http://47.100.5.48:18080/`（约 2 分钟） | **推测试环境** | 通过（直接接受）· 打回 |
| 测试环境就绪 | 测试部署 workflow 成功 | 「测试环境已更新」 | 地址 + workflow 链接 | 通过：接受这次改动，交付转为「待发布」（还不会上线） | **通过** | 打回 · 重新部署 |
| **待发布** | 交付 READY_FOR_RELEASE | 「可以发布到线上吗？」 | 测试地址 + PR 链接 | 发布：合并 PR #5 到 `main`，触发生产部署；部署成功后交付标记已上线（约 3–5 分钟） | **发布** | 打回 · 再看测试环境 |
| 已上线 | 交付 RELEASED | 「已上线」 | 线上地址 + release id | 结束。要改直接描述新需求，我会另开一条 | 提新需求 | — |
| **卡住** | 任务/交付 BLOCKED | 「卡住了」 | 单条失败原因（不贴日志） | 重跑：修复卡点后从 `origin/main` 新建工作区再跑一轮；也可以打回并说明要怎么改 | **重跑** | 打回（带意见）· 放弃 |

> 只有 4 个"必须问"的点：开工、测试部署、发布、卡住后的重跑。其余是状态更新，不给按钮也不算打扰。

## 2.5 prob-… 作为唯一追踪句柄

用户不需要记 `spec-…` / `task-…` / `dlv-…` / `run-…`（这些继续只出现在排查用的折叠详情里），但**最初的问题 id（`prob-…`）是需求的外部句柄**，处处可用：

| 用法 | 例子 | 行为 |
| --- | --- | --- |
| 查进度 | `prob-950662cc5b 现在到哪一步了` | 直接给出该需求的当前卡片（不看消息在哪个话题） |
| 发起操作 | `prob-950662cc5b 发布` / `prob-950662cc5b 打回：间距还是太挤` | 对该需求执行动作（仍过阶段门禁 + 角色权限 + 二次确认） |
| 话题里点名别的需求 | 在面包屑话题里说 `prob-950662cc5b 测试部署` | **以点名为准**，落到专辑页需求，并回一句"按你点名的 prob-950662cc5b 处理" |
| 追踪历史 | `prob-950662cc5b 有哪些进展` | 该需求的阶段时间线（提出 → 规格 → 各轮 Run → 测试 → 上线） |

规则：

1. **确定性优先**：`prob-[0-9a-f]{8,}` 的正则提取在模型之前完成（`src/command/intentTriage.ts` 的 rule 阶段），命中即作为指代，不交给模型猜；模型只在没有显式 id 时判断。
2. **点名胜过位置**：显式 prob id 与"所在话题绑定"冲突时，一律取 id，并在回执里说明按哪个需求处理——这正好兜住"用户在旧话题里发指令"的场景。
3. **卡片固定展示**：每张需求卡片都带 `prob-…`（页首或页脚，可复制），用户随手就能引用。
4. **其它 id 仍不面向用户**：`task-…`/`dlv-…`/`run-…` 粘进来时保持现有行为（忽略 + 一句引导），避免用户被迫搬运五层 id。
5. **越权/不存在**：id 不存在或无权限 → 回一句明确原因，不静默落到当前话题的需求。

## 3. 卡片结构与实现映射

复用现有积木（`src/channel/message.ts` 的 `section/markdown/actions`、`src/channel/feishu/cards.ts` 的按钮渲染、`src/server/session.ts` 的 `handleCardAction`）：

```text
📋 「专辑页「播放全部」间距」· 待发布 · prob-950662cc5b
✅ 测试环境已验证通过（workflow #38011430074）
🌐 线上地址：https://rehelu.net/albums/after-the-rain
🔀 PR #5 待合并
👉 下一步「发布」= 合并 PR #5 到 main，触发生产部署；成功后交付标记已上线（约 3–5 分钟）
[ 发布 ]  [ 打回并说明问题 ]  [ 再看测试环境 ]
（排查详情：spec-9d0df14cad · dlv-9128847051）   ← includeIds 折叠行
```

| 元素 | 落点 |
| --- | --- |
| 卡片渲染 | 扩展 `renderRequirementCard()`：`section`(标题+阶段) + `markdown`(证据) + `actions`(按钮) |
| 按钮 | `MessageAction{ id: "requirement.next", value: JSON }`，`value = { requirementId, action, stage }` |
| 回调 | `ChatSession.handleCardAction()` 增加 `requirement.next` 分支：解析 → `requirements.resolve()` → **校验 stage 与 requirementId** → `commandsForRequirementAction(action, view)` → dispatch |
| 门禁/措辞 | 完全复用 `requirement/application/actions.ts`（阶段不允许时返回 `ask`，直接回给用户） |
| 二次确认 | 打回/发布沿用"先回一句我理解成…，点确认才执行"（D9） |
| 幂等 | 重复点击/并发点击：stage 已变 → 回"这步已经做过了"，不重复执行 |
| 按 id 解析 | `RequirementResolver` 增加 `resolveByProblemId(problemId)`；消息/按钮都先尝试 prob id，再回落到话题绑定 |
| "下一步"文案 | 由 `commandsForRequirementAction` 的同一份决策产出（每个动作带一段 `nextStep` 说明），保证按钮与问句永不脱节 |

## 4. 谁在什么时候发这张卡

| 触发 | 现状 | 改为 |
| --- | --- | --- |
| Run 结束（`run.notified`） | 单独推 Run 卡 | 更新"当前卡片"的进展行；阶段推进时补发提问卡 |
| 交付 READY_FOR_RELEASE | 通知到默认群 | **发到该需求话题**，主按钮「发布」 |
| 交付 BLOCKED | 通知 | 发到该需求话题，主按钮「重跑」+ 失败原因 |
| 测试部署成功/失败 | 单独部署通知 | 合并进"当前卡片"（同一条消息更新，不再刷屏） |
| 打回（`review.changes_requested`） | 回执 | 回执 + "已重跑中"，不再发提问卡 |

去重：以"需求 + 阶段"为键，进入阶段时发一次；同一阶段内的事件只更新卡片，不重复提问。

## 5. 角色与按钮可见性

| 按钮 | 最低角色 |
| --- | --- |
| 开始开发 · 重跑 · 看看进展 | developer |
| 测试部署 · 通过 · 打回 | reviewer |
| 发布 | reviewer |

非授权用户点按钮 → 「这一步需要 reviewer 角色（你当前是 developer）」，不执行（现有 authorization 已具备）。

## 6. 边界

- 需求已 `RELEASED` 时点任何推进按钮 → 「已经上线，要改请提新需求」（与 TASK-1256 同措辞）。
- 话题锚点丢失/卡片不在该需求话题里 → 卡片落到主聊天并说明，按钮仍可用（`requirementId` 显式带上，不依赖会话绑定）。
- 同一需求 5 分钟内不重复发同阶段的提问卡（防抖）。
- 用户不用按钮、直接说人话 → 走现有意图解析，行为不变。
- 消息带 `prob-…` 但该需求与当前话题不同 → 以 id 为准，并在回执里写明"按 prob-… 处理"（不是静默改绑会话）。
- 消息同时带 `prob-…` 和 `dlv-…`/`task-…` → 以 `prob-…` 为准，其它 id 按"忽略并引导"处理。

## 7. 分期

| 阶段 | 内容 |
| --- | --- |
| P1 ✅ | 卡片含具体下一步文案 + 一键按钮 + 过期与门禁；卡片固定展示 `prob-…`；`prob-…` 可查进度、可发起操作（`resolveByProblemId` + 确定性 id 提取 + 点名胜过位置）；按钮复用 `commandsForRequirementAction`。主动发卡：Run 结束进「待验收」、交付 READY_FOR_RELEASE / BLOCKED |
| P2 | 通知合并成一张"当前卡片"（更新而非追加）；打回意见输入；按钮按角色显示/禁用（当前是点了之后由授权层拒绝）；BLOCKED 独立阶段（现在是"开发中"+重跑） |
| P3 | 按需求设置静默/只推主按钮；CLI 与聊天面口径对齐 |

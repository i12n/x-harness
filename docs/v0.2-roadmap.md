# v0.2 Roadmap（已采纳方向）

> 来源：2026-09-16 讨论确定。本文记录调整后的 v0.2 路线与节奏，
> 取代此前“直接堆 v0.2 功能”的默认理解。

## 核心判断

不要再围绕 `Task → Run → Agent` 堆外围功能。Harness 的核心对象升级为
「从问题到结果的完整闭环」：

```text
Problem
   ↓
Decision / Confirmation
   ↓
Task
   ↓
Execution
   ↓
Evidence
   ↓
Human Decision
```

## 执行顺序

```text
v0.1 全链路已跑通
        │
        ▼
① 真 Postgres + 真 Codex 组合 E2E（v0.1 封版）
        │
        ▼
② Problem Confirmation Loop
        │
        ▼
③ Multi Repository Task
        │
        ▼
④ Dependency DAG
        │
        ▼
⑤ GitHub Integration
        │
        ▼
v0.2 完整闭环
```

## P0 — v0.1 封版

- 真实 Postgres + 真实 Codex 组合 E2E（主线；已完成，见
  `npm run test:e2e:real`）
- 收尾工程项（非主线）：Run timeout、Run cancellation、migration version、
  CLI npm link、multi-worker race test

验收目标（已达成）：Repository → Task → Scheduler → Run → Worktree →
真实 Codex → Verification → Run SUCCEEDED → Task REVIEW → Events 完整 →
Workspace cleanup 全部串通。

## P1 — Problem Confirmation（下一步，唯一入口缺口）

> 进展（2026-09-16）：数据模型与存储已完成（`migrations/002_problems.sql`、
> `src/domain/problem.ts`、内存 + Postgres ProblemStore，含真库集成测试）。
> Confirmation Loop 已完成：Problem Analyzer（严格 JSON 解析 + codex
> `--json` 输出提取 + 历史问答回灌）、Confirmation Loop（analyze ⇄ answer，
> 最小充分信息即 CONFIRMED）、`problem.*` 事件
> （`migrations/003_event_problem_id.sql`）、`ai problem` CLI、Problem → Task
> 转换。真实模型验证：多轮澄清后 2 轮收敛到 CONFIRMED。
> 待做：Investigation / Specification 的自动化（当前由 `ai problem task`
> 手动桥接）。

解决的问题：**“用户随口说的一句话，如何变成一个可执行的 Task？”**

```text
Problem → Analyze → 需要确认？
                      ├── NO  → CONFIRMED
                      └── YES → Clarification → Answer → Analyze → 循环
   ↓
CONFIRMED → Investigation → Specification → Task
```

- 第一版只做 Confirmation Loop；**不**同时做完整 Autonomous Investigation，
  不引入 RAG / Memory / Reviewer 扩展
- 数据模型（首版）：`problems`、`problem_analyses`、`clarifications`、
  `clarification_answers`
- Problem 状态（MVP）：`INBOX → ANALYZING → NEEDS_INPUT ⇄ ANSWERED →
  ANALYZING → CONFIRMED → INVESTIGATING → SPECIFIED → READY`
- 事件复用现有 `events`（`problem.clarification.created/answered`、
  `problem.analysis.updated`、`problem.confirmed`）
- CLI（建议）：`ai problem create|list|show|confirm|answer`
- 详细设计稿：[Problem Confirmation Loop](problem-confirmation-loop.md)

## P2 — Multi Repository

- `Task → TaskTargets[] → Repository A/B/C`
- `Run → Workspace A/B/C`，多工作区隔离
- Repository 级 verification、多仓库 context

## P3 — Dependency DAG

- Task 依赖模型与校验
- Scheduler 从「READY Task」升级为「READY + 依赖满足 + 容量」
- Dependency recovery

## P4 — GitHub

- GitHub 作为 Adapter，而不是 Harness 核心：
  Harness Core（Repository/Task/Run/Workspace/Agent/Verification/
  Scheduler/Loop/Event）+ GitHub Adapter
- Issue → Problem、Task → Branch、Run → Commit/PR、PR status events

## 三个层次不要混

```text
Verification     机器可验证条件（代码是否满足 checks）
Reviewer         实现是否合理（工程判断，建议性）
Human Approval   人是否接受结果（最终决定）
```

Reviewer/Approval 已有雏形，暂不扩展能力，先接入完整生命周期。

## 当前决定

- 下一步优先做 P1 Problem Confirmation Loop（上游入口），
  Multi Repository / DAG / GitHub 排在其后。

## Phase 9 — Remote Execution & Isolation（新增，服务器化）

在 v0.2 主线之外新增 Phase 9：把“本地能跑”升级为“服务器长期运行”。
核心不是把 Node.js 部署上服务器，而是分离管理面与执行面：

```text
Control Plane: API / PostgreSQL / Scheduler / Loop / Worker Manager
Execution Plane: Container(Codex/Git/Node/测试) + Workspace(worktree)
```

- 隔离单位是 **Run**（Task 可多次 Run）：一个 Run = 一个 Container +
  一个 Worktree
- 安全底线：不挂 docker.sock、不挂宿主根目录、只挂当前 Run workspace +
  tmpfs /tmp、cap-drop ALL、no-new-privileges、非 root、资源限制
- 网络白名单属于 Execution Profile（按 Repository 技术栈配置），不写死核心
- Secrets 走 Secret Store，只注入当前 Run，不落 Repository/Task/Run/Event
- 不使用 Kubernetes/Kafka/Redis/RabbitMQ（触发条件见设计文档）
- 任务拆分：TASK-901..910，详见
  [Remote Execution & Isolation](remote-execution-isolation.md)
  - 进度：TASK-902（Worker → ExecutionManager → Agent/Verification +
    Repository executionProfile 绑定 + ExecutionContext + fake driver 全链路
    验证）已完成；TASK-901/908（Execution 生命周期契约、cleanup obligation、
    持久化、timeout/cancel、Worker 崩溃恢复、cleanup 失败重试）已完成；
    TASK-911/912/913（镜像/入口契约、`ExecutionDriver.exec()`、
    Codex/Verifier 容器内执行通路）已完成；
    TASK-910/905 已在真机（<验收主机>）验收通过（生命周期 8/8、隔离
    2/2、网络 2/2，宿主服务不受影响）→ **Phase 9 DONE**。
    下一步回到主线：Multi Repository Task → Dependency DAG →
    GitHub Integration

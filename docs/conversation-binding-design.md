> `conversation/service.ts`（`contextSinceAnchor`）、`server/index.ts`（intent 上下文按锚点裁剪）。
> 现场：2026-10-09 生产库 `conv-63e508dfcb`（新需求被投进旧话题，见 §0）。
> 关联：`requirement-interaction-redesign.md`（一个对象一个话题）、TASK-1243（话题锚点）、TASK-1244（user-level 动作）、TASK-1250（新需求不依赖旧需求）、TASK-1256（已合并交付不再重推）。

## 0. 现状与故障

现在的链路是两段拼起来的：

```text
入站消息
  → 会话定位：events.ts 只认 thread_id；无 thread 落到"chat 级会话"
  → 需求指代：resolver 用 conversation.subject_id 找 problem → spec → delivery → tasks
  → 出站路由：replyToMessageId = conversation.anchor_message_id（reply in thread）
  → 上下文：intent 只看该会话最近 12 条消息
```

2026-10-09 的真实故障（两个需求挤进一条飞书话题）：

```text
05:15  用户在群里描述面包屑需求（无 thread）→ chat 级会话 conv-63e508dfcb，锚点=05:15 消息
05:28  用户在同一话题里重发一遍        → 新会话 conv-bb97f8e963，绑定面包屑问题
09:08  用户描述专辑页间距（无 thread） → 落回 conv-63e508dfcb，绑定新问题
       ……但锚点仍是 05:15 的面包屑消息
       ⇒ 新需求的所有卡片 reply-in-thread 到 05:15 消息 ⇒ 飞书里与面包屑同话题
09:26  用户在该话题里说「部署到测试环境」→ 飞书带 thread_id ⇒ 判给面包屑需求 ⇒ 报错
```

根因不在判定规则，而在**"新需求要换话题锚点"这条不变量只写在旧命令路径上**（`server/session.ts` 里 `result.type === "problem.create"` 那段），TASK-1244 之后新需求走的是 user-level `create` 动作 → `handleRequirementAction()` → 直接 return，换锚点从未执行。

## 1. 不变量

1. **一个需求 = 一条飞书话题**；话题是需求级隔离单位。
2. 一条消息**最多绑定一个需求**，且绑定可解释、可重放（同一条 messageId 重放得到同一结论）。
3. **绝不在别人的话题里开新需求**；绝不把 A 话题的补充喂给 B 需求。
4. 绑定结果必须**可见**（回复里点出需求标题）且**可纠正**（一句话改指代）。
5. 绑定不依赖时间先后这种弱信号做硬判断——时间只用于排序候选。

## 2. 两层绑定模型

把"绑定"拆成两层，各自只回答一个问题：

### 第一层：会话定位（routing）

| 信号 | 结论 |
| --- | --- |
| 有 `thread_id` | 该话题的会话（不存在则新建，并继承本 chat 级会话的 subject） |
| 无 `thread_id`，但回复/引用某条消息 | **仍是 chat 级会话**（不为 parent/root 新建会话，避免历史被切碎），但记下"这条引用指向哪个需求"用于第二层 |
| 无 `thread_id` 且无引用 | chat 级会话 |

会话身份由 `conversations_external_idx (channel, chat, COALESCE(thread,''))` 决定，一个 chat 只有**一个** chat 级会话。

### 第二层：需求指代（referent）

在会话内决定这条消息说的是哪个需求，输出 `RequirementView` 或**候选列表**。

| 优先级 | 规则 | 例子 |
| --- | --- | --- |
| 1 | 显式指代：消息点名了某需求（标题/编号） | 「面包屑那条还是不对」 |
| 2 | 引用指代：回复的那条消息属于某需求 | 引用 Run 卡片说「这里为什么失败」 |
| 3 | 待办态：该需求正等输入（澄清答案 / 二次确认 / 打回意见） | 澄清卡片下的「仅调整这一处」 |
| 4 | 动作型：`show/reject/deploy/publish/rerun` 必须有指代 | 「通过」→ 需要知道通过哪条 |
| 5 | 陈述型：`create` → 判定"新目标"还是"改当前" | 见 §3 |
| 6 | 都不确定 | **先问**：列出候选（当前会话需求 + 本 chat 最近 3 条活跃需求，带阶段） |

## 3. 新目标 vs 修改当前需求

`create` 动作不代表一定是"新需求"。判定顺序：

1. 若消息**引用/回复**了当前需求的某条消息，且措辞是修改口吻（「还是不行」「再改一下」「间距改成 24」）→ 判为**修改**：走 `reject` / `rerun` / `advance`，不开新需求。
2. 若当前需求处于 `clarifying`（等澄清）或 `awaiting_acceptance`（等验收）→ 默认判为对该需求的补充，除非消息明显在描述另一件事（新的对象/页面）。
3. 否则判为**新需求**，并且按 §4 落地。
4. 置信度低 → 问一句（"这是要给「X」再加一条，还是一个新需求？[改这条][新需求]"），不做静默选择。

## 4. 新需求怎么落地（关键规则）

| 场景 | 做法 |
| --- | --- |
| chat 主流程（无 thread）里描述新需求 | 开新需求 → **把该 chat 级会话的锚点换成这条消息**（= 新需求的话题根）→ 本轮回复也 reply-in-thread 到它 → 上下文窗口从锚点起算。旧需求的话题不受影响。 |
| **别人的话题里**描述新需求 | **不在该话题开新需求**。回复一句"这像是个新需求，我另开一条"，然后在 chat 级会话落地（同上）。若判不准，先问「改这条」还是「新需求」。 |
| 话题里的话题（用户回复卡片） | 归该话题的需求，不新建。 |

这条规则是本次事故的反面：chat 级会话是**入口 + 当前需求指针**，不是"一个 chat 一个固定需求"。它通过换锚点轮转，历史消息靠 §5 的窗口裁剪与新需求隔离。

## 5. 上下文按锚点裁剪

`intent` 原本取该会话最近 12 条消息，跨需求混在一起，是"把新需求识别成补充"的另一个诱因。规则（**已实现**）：

- 会话有锚点时，上下文 = **锚点消息起**的消息（`ConversationService.contextSinceAnchor`，锚点本身保留——它就是需求描述），再加需求摘要。
- 换锚点 = 换上下文边界，历史不再污染新需求的判断。
- 锚点缺失时才退回"最近 N 条"。

## 6. 数据与原子性

- `conversations.anchor_message_id` 已有；上下文裁剪需要锚点时间 → 由 `conversation_messages.external_message_id` 反查，或加 `anchor_at` 列（二选一，倾向前者，不新增列）。
- **开新需求 / 换锚点 / 换 subject 必须一起成功**：现在 `problem.create` 成功后才 setAnchor，中间任何一步失败就会出现"subject 已换、锚点没换"的半截状态（正是本次事故）。做法：把这三步收进同一个 application 服务方法（`requirement.createFromMessage(conversationId, messageId, statement)`），失败即回滚并告警。
- 重放安全：`external_message_id` 唯一约束保证重投不重复开单。

## 7. 可解释性与纠正

- 每条回复点名需求标题与阶段（TASK-1249 已有基础）。
- 绑定存疑时给候选按钮而不是猜。
- 新增纠正路径：「不对，我是说面包屑那条」→ 解析为显式指代 → 本次动作绑定该需求；并记住这次纠正（换回该会话的 subject/锚点）。

## 8. 迁移与补救

- 历史 chat 级会话锚点可能错位（`conv-63e508dfcb` 的锚点是 05:15 那条旧消息）。一次性脚本：把锚点改为该会话**当前 subject 对应问题**的首条相关消息；找不到就设为该会话最近一条入站消息。
- 迁移只改锚点，不动消息与 subject。

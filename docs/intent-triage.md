# 意图分诊：什么该建开发任务，什么只是查询（需求 + 方案设计）

> 状态：**P0 + P1 已实现并部署**（2026-09-28）。判定矩阵用真实模型回归 17/17。
> 相关现状见
> [conversational-interface.md](conversational-interface.md)（命令目录、授权、幂等）
> 与 [problem-confirmation-loop.md](problem-confirmation-loop.md)（需求澄清）。

## 1. 问题

群聊/私聊里同时存在"**问**"和"**做**"两类消息，而现在只有一层提示词把消息映射
成命令。两个方向的误判代价完全不同：

| 误判方向 | 后果 | 严重度 |
| --- | --- | --- |
| 提问 → 建开发任务 | 白跑一次问题分析（token 成本）、任务列表被无关条目污染、需人工清理 | 中 |
| 需求 → 当成提问回答 | **活没人干**，用户却以为机器人已经知道了，静默丢失 | **高** |
| 操作指令 → 当成需求 | 该审批的没审批、该停的没停，流程卡住 | 高 |

值得注意的既有安全网：**任务只能由 `spec.plan` 产生，Run 只能由 `task.run`
触发**。所以"把提问误判成需求"最坏只多出一条待确认的 Problem，不会自动开工。
因此本设计的主要目标不是防"误开工"，而是：

1. **不丢活**：真正的需求绝不能被"回答"掉；
2. **不白烧**：纯提问不触发问题分析与任务链路；
3. **可解释**：每次判定留下理由，误判可复盘。

## 2. 术语：四类意图

| 代号 | 名称 | 定义 | 副作用 |
| --- | --- | --- | --- |
| **Q** | 查询 | 只想了解已经存在的事实 | 无（只读） |
| **A** | 操作 | 对**已存在**的对象下达动作（运行/取消/审批/打回/发布/改配置/授权） | 受控、可审计 |
| **N** | 新工作 | 要求改变系统行为或交付物，需要人写代码 | 进入 Problem → 澄清 → 规格 → 任务 |
| **C** | 闲聊/其他 | 既非查询也非工作（寒暄、能力询问、与本系统无关） | 无 |

**"建开发任务"特指 N。** Q / A / C 都不该产生 Task。

## 3. 判定原则（硬规则）

1. **默认不是工作。** 只有明确表达"要改变什么"时才是 N；问句、寒暄、状态确认
   一律不进 N。
2. **疑问结构优先判 Q。** 出现"哪些 / 哪个 / 有没有 / 是不是 / 为什么 / 怎么还没 /
   进行到哪"等结构，且**没有**明确的祈使对象时判 Q——即使句子里提到了
   Task/Run/仓库等名词。
   - `为什么 task-3 失败了` → Q（不是在要求"重跑 task-3"）
   - `task-3 失败了，重跑一下` → A
3. **有对象、有动词、有期望变化 → N。** 描述现象或期望（"首页没有空状态提示"、
   "登录偶尔 500"）就属于 N 的输入；**不要求用户说"帮我做"**。
4. **对已有对象的动作判 A，不判 N。** 已存在 task/run/delivery 时说的动作
   （运行、取消、通过、打回、发布、重启、改配置、授权）属于 A。
5. **拿不准就问，不要猜。** 置信度低于阈值，或 N 与 Q 都可能成立时，回一条二选一
   确认（见 §4.3），**既不直接建 Problem、也不直接回答**。
6. **绝不静默吞掉。** 任何被判为 C 的消息，回复里必须带一句"如果这是要我做的事，
   请直接说要改什么"，把丢失风险交回给人。

### 3.1 判定所用信号

| 信号 | 偏向 |
| --- | --- |
| 结构化前缀（`设置 KEY 值`） | 直接走确定性路由，不进模型 |
| 出现已知 id（`task-`/`run-`/`spec-`/`dlv-`/`prob-`） | Q 或 A（取决于动词） |
| 动作动词（运行/取消/通过/打回/发布/重启/授权/改成） | A |
| 疑问结构 | Q |
| 现象描述 + 期望（"…没有…""…应该…""…报错…""能不能支持…"） | N |
| 纯寒暄 / 能力询问 | C |

### 4.3 低置信度确认话术

```text
我不确定这是要我开工，还是只想了解情况：
  要我开工   → 回复「开工」并补一句期望结果
  只是问一下 → 回复「我只是问问」
```

用带按钮（actions）的卡片承载，避免再让模型解析一次自由文本。选择"开工"之后才
调用 `problem.create`，并把原句作为 statement。

## 5. 方案设计

### 5.1 架构位置

```text
IncomingMessage
      │
      ├─(1) 确定性路由：结构化命令 / 已知 id + 动作动词
      │
      └─(2) IntentRouter：LLM 分类 → { kind, command?, confidence, reason }
                    │
        ┌───────────┼───────────────┬────────────────┐
        ▼           ▼               ▼                ▼
      Q 查询      A 操作          N 新工作          C 其他
    只读命令   现有操作命令    problem.create    能力说明
        │           │               │                │
        └───────────┴───────────────┴────────────────┘
                      CommandDispatcher
              （校验 → 授权 → 幂等 → 路由 → 审计）
```

**IntentRouter 只产出判定，不产出副作用**；执行仍走既有命令管道，因此授权、
幂等、审计一条都不少。这与 `ScriptedIntentEngine` / `LlmIntentEngine` 的现有
边界一致：引擎只能产出 Command，拿不到内部能力。

### 5.2 两段式分类

- **第一段（确定性，零成本）**：结构化前缀（`设置 KEY 值`）、已知 id + 动作动词
  的固定句式。命中即直接路由，**不进模型**——密钥路径已经是这个做法。
- **第二段（模型）**：输出结构从"一个命令或 null"升级为

  ```json
  {"kind": "query|act|work|chat", "command": {...}|null,
   "confidence": 0.0, "reason": "…"}
  ```

  提示词写明 §3 的六条规则，并附 §4 判定矩阵作为 few-shot。
- **回落**：`kind=work` 且 `confidence < 0.6` → 确认话术；`kind=chat` → 能力说明；
  解析失败 → 能力说明（**绝不默认建 Problem**）。

### 5.3 命令目录补全（Q 类必须先有落点）

一条铁律：**Q 类判定必须有对应命令，否则"不回答"那个 bug 会重演**。

| 缺口 | 现状 | 处理 |
| --- | --- | --- |
| 仓库 / 任务列表 | 已补 `repository.list`、`task.list` | 已完成 |
| 失败原因 | `run.show` 只渲染状态与 check 输出 | 把 `latestFailure` 事实接进渲染（数据已有） |
| 最近发生了什么 | 无 | 新增 `run.list {limit?}` |
| 当前有哪些问题 | 无 | 新增 `problem.list {status?}` |
| 交付 / 发布总览 | 只有 `delivery.show <id>` | 新增 `delivery.list` |

### 5.4 N 类的防抖与澄清

N 的唯一出口是 `problem.create`，之后**立刻**进入既有的 Problem Confirmation
Loop：分析器判断信息是否足够，不够就提结构化澄清。因此：

- 含糊需求（"优化一下首页"）不会直接变成任务，而是先变成一组待回答的问题；
- **不需要**为分诊新造一套需求确认机制，复用澄清循环即可；
- 任务是 `spec.plan` 的产物，Run 是 `task.run` 的产物——分诊永不越级。

**目标仓库来自对话上下文，不来自环境变量。** 意图提示词里会带上已注册仓库的
`id (name)` 清单，模型据此在 `problem.create.repositoryId` 上填出用户当前点名、
同一会话里此前谈到的仓库，或唯一已注册的那一个；判断不出来就留空（由澄清循环
追问），而不是猜。这样多仓库场景无需 `AI_DEFAULT_REPOSITORY_ID` 之类的部署默认值。

### 5.5 可观测性

每次判定写一条事件，便于复盘误判与统计成本：

```json
{"type": "intent.classified",
 "payload": {"kind": "work", "command": "problem.create",
             "confidence": 0.82, "stage": "llm", "reason": "描述了期望状态"}}
```

配合 `conversation.show` 与 `ai event list --type intent.classified`，可以回答
"这条消息当时被判成什么、为什么"。

### 5.6 成本控制

- 确定性命中 → 0 次模型调用；
- 分类与命令映射合并为**一次**模型调用（不额外加一轮）；
- 低置信度确认话术不再调模型（按钮选择走确定性路径）；
- `work` 之后的澄清轮次沿用现有 Confirmation Loop，本身有界。

### 5.7 边界（刻意不做）

- 不做需求去重（"这是不是已经建过的 Problem"）——先积累真实数据；
- 不做跨会话需求聚合；
- 不修改 Problem / Task / Run 生命周期与状态机；
- 不让分诊直接创建 Task 或触发 Run。

## 6. 验收标准

1. §4 的 25 条判定矩阵全部符合期望（单测固定，模型回归另跑）；
2. 任意 Q 类消息**不产生**领域写入（除对话记录与审计事件）；
3. `kind=chat` 的回复必须包含"如果这是要我做的事…"出口；
4. 分诊判定 + 命令映射合计**不超过 1 次**模型调用；
5. 密钥类消息仍不进模型、不入库（现有行为不回退）；
6. 每次判定都有 `intent.classified` 事件，字段齐全。

## 8. 风险

| 风险 | 缓解 |
| --- | --- |
| 模型把 N 判成 C，需求被当成寒暄 | C 的回复强制带"要开工请明说"出口；`intent.classified` 可复盘 |
| 分类增加一次模型调用导致变慢 | 与命令映射合并为一次；确定性前缀零成本 |
| 用户养成"什么都丢一句"的习惯 | 低置信度必须确认，不猜；`work` 仍需澄清循环收敛 |

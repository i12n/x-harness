# TASK-1232 规划粒度：约束与验收标准不再拆成任务

> 上级设计：[autonomy-redesign.md](autonomy-redesign.md) §1.1 / §3。
> 现场证据：本文件 §1。前置：TASK-1224（plan item 的验收子集与检查）已上线。

## 1. 现场（2026-10-08 实测，生产库）

交付 `dlv-487e422b44`（x-music 移动端按钮间距）被规划成 3 个任务：

| 任务 | 内容 | 本质 |
| --- | --- | --- |
| `task-…-0` | 「播放全部按钮与上方标签的间距被增大到合理视觉间距」 | **可交付物** |
| `task-…-1` | 「调整只作用于移动端专辑页…不改变桌面端及其它页面」 | **范围约束** |
| `task-…-2` | 「不同移动端宽度下布局稳定、不重叠或错位」 | **验收标准** |

后果（不是理论，是实际发生的）：

```
run-5627523d52  SUCCEEDED → 评审："empty diff and no changed files,
                            while all five acceptance criteria are unverifiable"
                          → request_changes → 退 READY → 重试
run-ef6c3dae7b  SUCCEEDED → 同样 retry
run-0b0cd8a8e6  RUNNING   → 第 3 次（maxAttempts=3）
```

即：**约束/验收标准没有可交付的改动，必然产生空 diff；评审只能要求返工；重试耗尽进 BLOCKED。**
这类任务永远到不了 DONE，把交付（`dlv-…`）卡在 `IN_PROGRESS`，也让"验收通过 → 合并上线"走不完整。

## 2. 拍板决策

| # | 决策 | 理由 |
| --- | --- | --- |
| D1 | **任务 = 能独立验证、且能产生改动的交付物**。约束与验收标准不是任务 | 定义先行，否则一切规则无的放矢 |
| D2 | 约束与验收标准**并入所属交付物的 acceptance / checks**，不产生新任务 | 它们本来就该是"怎么算做完"，不是"要做的一件事" |
| D3 | 判定用**确定性规则**（可复现、可审阅），不做纯模型自由判断；模型最多给候选、规则做终审 | 与 `risk.ts`、`intentTriage` 的既有原则一致 |
| D4 | 判定发生在**规划后、建任务前**的一道整理步骤；被判定为非交付物的条目**合并**进最近的交付物条目，而不是丢弃 | 信息不丢，只是换了载体 |
| D5 | 无法判定的一律**保留为任务**（保守） | 宁可多一个任务，不可吞掉一个交付物 |
| D6 | 本次只改**新规划**；已经存在的历史任务不自动改写 | 历史数据改动风险大，单独处理（见 §6） |

## 3. 判定规则（确定性，草案）

一个 plan item 若命中以下任一条，即**判为非交付物**：

| 规则 | 例（来自现场） |
| --- | --- |
| 以范围限定词开头/含限定语："只/仅/不得/不影响/保持不变…" | 「调整**只**作用于移动端…**不改变**桌面端」 |
| 描述的是**判定条件**而非改动："…不重叠/不报错/保持一致/通过…" | 「不同宽度下布局稳定、**不重叠或错位**」 |
| 无动词性改动目标（纯名词短语或纯标准句），且其 `checks` 为空 | 同上两条 |

命中后：把该条目的文本追加到**同一交付内最近一个交付物条目**的 acceptance（并保留其 checks 映射），
然后从任务列表里移除。交付物条目**一个都没有**时，按 D5 全部保留。

## 4. 落点

| 文件 | 改动 |
| --- | --- |
| **新增** `src/specification/domain/planGranularity.ts` | 纯函数 `isDeliverable(item)` / `mergeNonDeliverables(items)`（规则集中在这里，可单测） |
| `src/specification/application/planning.ts` | `materializeTasks` 之前调用整理步骤（一次，规则只有一份） |
| `src/server/specificationBootstrap.ts` | 同上：bootstrap 产出 workItems 时走同一条整理路径 |
| 事件 | 整理结果写 `plan.granularity.adjusted`（合并了 N 条、各并入谁），事后可审计 |

## 5. 验收（可执行）

1. 三条现场数据（见 §1）→ 只产出 **1 个任务**，另两条的文本出现在该任务的 acceptance 里。
2. 全是交付物的需求 → **一条都不合并**（回归保护）。
3. 命中有歧义、无法判定 → 保留为任务（D5）。
4. 合并后 `checks` 不丢：原条目带的检查仍出现在目标任务的 checks 中。
5. 事件 `plan.granularity.adjusted` 记录合并明细。

## 6. 不在本次范围

- 历史任务（`task-…-1`/`-2` 已经存在、且卡在重试/BLOCKED）不自动改写；处理它们的路径是"关闭/跳过任务"（另一个小任务），或人工收口。
- 任务级重试策略（空 diff 是否该重试）不动——本次只保证"**不该成为任务的不会成为任务**"。

## 7. 回滚

整理步骤是一个纯函数，恒返回"全部保留"即回到今天的行为；事件保留审计轨迹。

## 3. 八个关键问题的结论

### 3.1 Phase 9 Execution 与 Phase 12 Run/Execution

```text
RunStore         attempt 状态机（QUEUED…LOST）+ runs_active_task_idx（唯一 active run）
ExecutionStore   资源生命周期（CREATING→RUNNING→CLEANED / CLEANUP_FAILED 重试）
Worker           唯一同时写两者的地方
Loop             崩溃后的 reclaim（以 executions.mounts 为权威）
```

判断：边界成立，无需重构；存在一处事实重复（见 §4 #6）与一处命名层级问题（#9）。

### 3.2 Phase 10 Multi-Repository 与 Phase 12 Specification/TaskTarget

```text
specification_targets（规格声明）
        ↓ PlanningService 显式映射（role/position/baseRef 复制，required 默认 true）
task_targets（执行单元，带 id/required）
```

判断：分层有意为之，映射显式；两点需决策（#7 required 语义、#8 修订传播）。

### 3.3 Phase 11 Command/Conversation 与未来 Console/Web UI

判断：「统一入口」只成立一半 —— CLI 中仅 `spec.*` / `delivery.*` 走 Command 层，
`task show/run`、`run.*`、`problem.*`、`review approve/reject` 等仍直连旧命令函数
（`src/cli/commands/*`）。未来 UI 前必须统一（#3）。

### 3.4 Problem → Specification → Task 是否已是稳定主链

判断（本次盘点最重要发现）：**模型与测试是稳定主链，生产入口缺失**。

```text
· `new SpecificationService` 在 src/ 无任何调用点（仅 PlanningService/DeliveryService 在 CLI 构造）
· Command 目录无 spec.create / spec.ready（仅 spec.show / spec.plan）
· 旧路径 `ai problem task <id>`（convertProblemToTaskCommand）仍可绕过主链直接建 Task
```

这是 Phase 13 的第一个必做项（#1、#2）。

> **已修复（TASK-1210，2026-10-01）**：`spec.create` / `spec.update` /
> `spec.ready` 已加入 Command 目录并有 `ai spec …` CLI，`SpecificationService`
> 现在由 `src/cli/index.ts` 构造；`ai problem task` 保留为标记 deprecated 的
> 逃生口（执行前打印警告）。详见
> [v0.2-roadmap.md](v0.2-roadmap.md) §Phase 13。本节其余文字保留为 v0.2
> 盘点当时的事实记录。

### 3.5 Scheduler / Loop / Worker 是否职责重叠

```text
Scheduler 选 + 建 Run       Worker claim/执行/验证/完成/清理       Loop 编排/恢复/取消/Delivery reconcile
```

主划分清晰；三处具体重复：retry 终态策略（#4）、并发开关（#5）、清理职责三分（记录，不视为债）。

### 3.6 Verification / Evidence / Failure Evidence 事实模型

```text
run.result.targets[].checks[]         （per-target，renderer 读）
run.error.verification[]              （per-check 扁平）
run.error.failingTargets[].checks[]   （per-target 失败子集）
extractFailureEvidence(run)           （TASK-1207 domain 摘要）
collectRunTargets()                   （renderer 归一化 + fallback）
```

判断：可用但非唯一事实源（#10）。

### 3.7 Delivery / Release 与 CI/CD

判断：当前 Release 只是记录，明确停在 Human Release Boundary ✓。
进入 CI/CD 前必须先有 **Release 的 commit/artifact 指纹**（现在 Run 只记
workspace/branch，没有 commit SHA），否则 PR/Merge 无从锚定（#5）。

### 3.8 TASK-1209 test typecheck gate

```text
事实：tsconfig include 仅 ["src"]；把 tests 全量纳入类型检查 → 17 个既有错误
影响：Gate 1 对 17k 行测试零类型保护（Step 3 已因这点漏过一个多余属性）
注意：新增 typecheck(tests) 会改变 Gate 定义 → 必须作为新 Task + 新 Acceptance
```

判断：值得做，建议作为 Phase 13 首批基础设施任务；本版本不做。

## 6. 真实环境验证期间的分流规则（重要）

真实环境验证发现问题时，**先分类，再决定是否动代码**：

```text
环境问题        → 记录到环境验证文档；修环境，不改代码
实现 Bug        → 只允许在「Phase 9–12 frozen behavior 无法成立」时开修复 Task
已知技术债      → 记入 §4，进入 Phase 13 backlog；本版本不修
新需求          → 记入 Phase 13 候选；不在验证期夹带实现
```

判定口径：冻结的验收证据（[phase12-acceptance.md](phase12-acceptance.md) §48）
在真实环境**重复成立**即视为通过；只有 frozen behavior 在新环境中不成立，才算
需要修复的实现 Bug。

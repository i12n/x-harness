### 7.1 TASK-1216 Interactive Card Multi-select & Callback Fix

来源：线上飞书机器人点击卡片选项后客户端报 **200672**。排查结论：
`FeishuLongConnection` 只注册了 `im.message.receive_v1`，没有注册
`card.action.trigger`；SDK 的 `EventDispatcher.invoke` 找不到处理器时返回字符串
`"no card.action.trigger event handle"`，飞书把它当成非法的卡片回调体。

方案（保持 v0.1/v0.2 的"最小核心"约束，不改数据库、不改领域模型）：

- **回调通道**：长连接注册 `card.action.trigger`，把事件体交给
  `ChatSession.handleCardAction`；每次点击都必须回一张合法卡片，客户端不再报
  200672。
- **多选控件**：`MessageBlock` 新增 `choice` 块（`options` + `multi` +
  `submit`）。飞书渲染成"每个选项一个 toggle 按钮 + 一个提交按钮"；点击选项
  同步重渲染卡片（回调响应即新卡片），提交按钮一次带上全部已选值。
- **选择状态**：`CardRegistry`（部署层，内存、有界）按消息 id 记住卡片与选择；
  重启丢失的代价只是重新选一次，不进数据库、不进领域。
- **提交不阻塞回调**：回答澄清会触发模型调用，可能超过飞书 ~3s 的回调预算，
  所以先回一张"已提交，正在处理…"的卡片，再异步执行命令并把结果作为新消息发回。
- **一次提交多个选项**：`problem.clarification.answer` 命令新增 `optionIds`
  字段；`ProblemService.answer` 把多选展开成"由所提供选项标签拼成的文本答案"
  （单选仍走原来的 `optionId` 精确路径），因此无需迁移 `clarification_answers`。
- **评审卡修复**：按钮原来携带 `run.id`，而 `review.approve` /
  `review.request_changes` 要求 `taskId`，即使补了回调也无法路由；改为携带
  `{"taskId": …}`，并让两个按钮走同一条可用的回调通道。
- **批量评审卡**：新增 `review.list`（列出全部 REVIEW 任务，一张卡片 + 一个
  多选组）与 `review.approve_batch {taskIds: string[]}`（逐任务 best-effort
  通过 + 发布，返回每个任务的结果）。`choice.submit.selectionField` 决定勾选值
  写进哪个字段（批量评审用 `taskIds`，澄清用默认的 `optionIds`）。触发方式：
  聊天里说 `待评审`（确定性规则）或让模型路由到 `review.list`。
- 测试：`tests/cardActions.test.ts`（解析 / 选择 / 渲染 / session 路由）、
  `tests/feishuLongConnection.test.ts`（注册回归）、
  `tests/problemConfirmationPipeline.test.ts`（多选作答三例）、
  `tests/rendering.test.ts`（评审卡 payload）。

### 7.2 TASK-1217 Execution Image Provisioning & Registration Gate

来源：`run-06220e712a` FAILED，`error` 原文 `Unable to find image
'harness/execution:base' locally`。`repo-x-music` 通过 CLI 注册时没带
`--exec-image`，落到核心默认值 `DEFAULT_EXECUTION_IMAGE = harness/execution:base`；
而部署文档/Dockerfile 只构建 `harness/execution:node22`。容器在 Run 的
`start` 阶段起不来，三次 attempt 全挂在同一原因上，任务被判 BLOCKED。

根因是**职责缺位**：镜像的构建没有归属（install.sh 只起 Postgres 和迁移），
存在性也没有任何阶段校验（`validateExecutionProfileContract` 只看 profile 的
形状，`harness/execution:base` 前缀合法，能通过）。

三段职责现在是：

```text
部署/装机   构建镜像（需要网络 + apt + codex）        → deploy/install.sh
注册仓库    校验镜像本机存在，缺了就拒绝（fail fast） → ai repository create
Run 执行    拉起容器 + docker exec 驱动               → Worker / ExecutionManager
```

- `deploy/install.sh`：构建 `harness/execution:${AI_EXECUTION_RUNTIME:-node22}`
  与 `harness/execution-proxy:latest`（已存在则跳过），并把默认回退名
  `harness/execution:base` 打上 tag——它才是没传 `--exec-image` 时真正会用的名字。
- `src/execution/imageCheck.ts`：`docker image inspect` 的封装，产出可执行的
  缺失说明（构建命令 + `--exec-image` 备选 + `docker images` 自查）；
  checker 可注入，便于离线测试。
- `ai repository create`：注册前校验**生效的**镜像（显式 flag 或默认值），
  不在本机就直接拒绝并给出修复步骤；`--skip-profile-check` 为显式逃生口。
- `serve` 启动 preflight：按仓库逐个校验镜像，缺的在日志里点名——
  存量仓库（如本次的 repo-x-music）不用重新注册也能被发现。只告警，不阻止启动。
- 测试：`tests/executionImageCheck.test.ts`（inspect 成功/失败/空名、注册门禁）。

### 7.3 TASK-1218 Repository Profile Update & Preflight

来源：`run-3eb14bb582` FAILED，卡片只显示 `Verification: FAIL — no verification
commands configured`。深挖事件才发现真正的第一因被盖住了：

```
AgentStarted
AgentFinished {exitCode: 1}          ← 2.1 秒就退出：agent 根本没跑起来
VerificationFailed {no verification commands}
```

`repo-x-music` 注册时一条执行参数都没给，整套落到"最严格默认档案"：
`network=none`（容器没有任何出网，够不到模型服务）、`secrets=[]`（`AI_CODEX_CONFIG`
声明的 `env_key=DEEPSEEK_API_KEY` 没人注入）、`verification.commands=[]`
（验证按设计必然 FAIL）。而当时**没有任何命令能修改已注册仓库的档案**，只能重新注册。

- **`repository update`**（CLI，`src/cli/commands/repositoryCommands.ts` +
  `RepositoryStore.updateRepository`）：补 `--verify` / `--exec-image` /
  `--network` / `--allow` / `--secret` / `--git-push` / 资源限制。**部分是部分**：
  只改传进来的字段，其余保持原值，避免一个旗标敲错把跑得通的档案重置成默认值。
  domain 层 `applyRepositoryUpdate` 负责合并与校验（含 URL 合法性）。
- **档案门禁前移**（`src/execution/profileGate.ts`）：`collectProfileIssues`
  一次列出所有会让每个 Run 失败的问题——没有验证命令、镜像不存在、声明的 secret
  在服务环境里解析不出来、`network=none`（agent 够不到 provider）、
  `restricted` 但允许列表里没有 provider 域名。provider 域名从
  `AI_CODEX_CONFIG` 的 `model_providers.*.base_url` 取，回退 `AI_LLM_BASE_URL`。
  - 注册/更新（CLI）只跑**与环境无关**的检查（镜像、验证命令）——操作者 shell 的
    环境不等于服务环境，用它会误报；
  - `serve` 启动 preflight 带上服务环境跑**全部**检查，逐仓库点名，只告警不拦截。
  - 逃生口：`--skip-profile-check`。
- **首因可见**（`src/channel/rendering/run.ts`）：run 卡在 `run.exitCode` 非 0 时
  先打印 `**Agent** codex 以退出码 1 结束 —— agent 自身先失败，下面的验证结果
  通常只是后果`，不再让验证失败掩盖 agent 失败。
- 测试：`tests/profileGate.test.ts`（12 例，含用服务环境复现 repo-x-music 的三处
  问题）、`tests/repositoryUpdate.test.ts`（5 例）、`tests/rendering.test.ts`
  新增 agent 退出码两例。

### 7.4 TASK-1219 自动开始（auto intake + auto run）

设计稿：[task-1219-auto-start.md](task-1219-auto-start.md)。

桥本来就存在（Task Intake，plan section 九），但只有人能动它：planning 产出
INBOX，scheduler 只认 READY。实测 x-music 那轮 = 3 个任务 = 3 次人工启动 + 3 次人工审批。

- `TaskIntakeService` 把 intake 规则从 CLI 命令里抽出来（一份规则两个调用方），
  issues 随结果返回而不是只打印
- `PlanningService` 只对**新建**任务跑 intake（对已完成任务重跑会把它复活），
  所以 planning 结束时任务已是 READY，调度器下一跳直接开跑；BLOCKED 的带上原因
- `AI_AUTO_START`（默认 true）在服务与 CLI 两处控制装配；置 false 完全回到人工模式
- 成本护栏同批落地（自动开始会放大重试代价）：`AI_RUN_TIMEOUT_MS` 默认从 0 改为
  30 分钟；env 布尔值接受 false/off/0/no
- 测试：`tests/autoStart.test.ts`（8 例：intake 后 READY、off 时 INBOX、仓库缺失 →
  BLOCKED + 事件、replay 不重复 intake、聊天文案三分支、30 分钟默认值）+
  `tests/serverConfig.test.ts` 开关两例

### 7.5 TASK-1224 拆分收敛（requirement ↔ acceptance ↔ checks）

设计稿：[task-1224-plan-granularity.md](task-1224-plan-granularity.md)。

planner 原本「一条 requirement = 一个任务」，于是约束和验收标准也会变成任务。

- derive 契约新增 `workItems`：每个工作项自带 `acceptance`（索引子集）与
  `checks`（可执行检查）；prompt 明确「约束/验收标准不是工作项」
- **harness 侧确定性修复**（`specification/application/workItems.ts`）：越界索引丢弃、
  无 check 的工作项并入相邻项、acceptance 集相同的合并、未被认领的 acceptance 并入
  最后一项、全部不合格则退化为整份 spec 一个任务
- planner 消费 `workItems`（并在使用时再修一次，任何写入路径都逃不过）；
  没有 workItems 的旧 spec 行为不变
- 任务只继承**自己那部分** acceptance，checks 存进任务 constraints —— 为
  TASK-1220（acceptance→checks）铺路
- 存储走 `specifications.constraints`，**不加迁移**
- 测试：`tests/workItems.test.ts`（13 例，含 x-music 形状回归：3 条 workItem →
  1 个任务且覆盖全部 5 条验收；derive 归一化；任务继承子集）
